# Complexity Changes by Version

Every built-in function has a **complexity** cost, charged against a script's per-transaction complexity limit. Several built-ins get cheaper (rarely, more expensive) at a later standard library version, independent of any change to their arguments or return type — a script recompiled at a higher `STDLIB_VERSION` can pass where it previously failed the complexity limit, with no code change.

```{note}
Verified against node-scala v1.7.0. Generated by `docs/scripts/extract_ride_complexity.py` in this repository, run against a checkout of node-scala's `lang` module — see that script's docstring for exactly what it does and does not capture. Re-run it after every node-scala release to catch drift; a diff means this table needs updating.
```

Where a function has more than one row, each row is a distinct overload (different argument types) with its own cost curve — the extraction can't attach argument types to a row, only the version-to-cost map, so use the {doc}`function reference <03_functions>` to tell overloads apart by signature.

## Coverage

This table only includes functions whose cost is set directly with a string literal name — `NativeFunction("name", Map(...), ...)`. Some costs are set through a helper (for example the BigInt arithmetic operators `+`, `*`, `/`, `%`, all `V5 -> 8L`/`V5 -> 64L`, stepping to `1L` at V8, defined via a shared `bigIntArithmeticOp` helper) and aren't captured here, since attributing them correctly would mean guessing at the helper's argument order rather than reading it off a literal. Treat this page as a documented lower bound on what changed, not an exhaustive list — the {doc}`Standard Library Versions <08_stdlib-versions>` page covers every genuinely *new* function and structure field, which this page does not repeat.
